```sh
npx @eoria/cli add date-picker
```

Needs `@react-native-community/datetimepicker`, a native module. Expo projects add it with `npx expo install @react-native-community/datetimepicker` and rebuild the development build. The item also brings `dialog`, `button` and `text`.

## Usage

```tsx
import { DatePicker } from '@/components/ui/date-picker'
import { Calendar } from 'lucide-react-native'

const [date, setDate] = useState<Date | null>(null)

<DatePicker value={date} onValueChange={setDate} icon={<Calendar />} />
<Button variant="link" onPress={() => setDate(null)}>Clear</Button>

<DatePicker mode="time" placeholder="No alarm" />
<DatePicker
  mode="datetime"
  minimumDate={new Date()}
  formatValue={(d) => d.toLocaleString('pt-PT', { dateStyle: 'full', timeStyle: 'short' })}
/>
```

A departure in Tokyo time, on a 24-hour clock, in 5 minute steps:

```tsx
<DatePicker
  mode="datetime"
  value={departure}
  onValueChange={setDeparture}
  timeZoneName="Asia/Tokyo"
  locale="en-GB"
  is24Hour
  minuteInterval={5}
/>
```

| `mode`                                   | `date`, `time`, `datetime`                                       | `date`            |

| `display`                                | `{ ios?, android? }`, the picker style per platform              | see below         |
| `placeholder`                            | text shown with no value                                         | `Select a date`   |

## Notes

eoria does not draw a calendar. On iOS the field opens a bottom Dialog holding the system calendar for `date` and the wheels for `time` and `datetime`. The value is committed when the user taps Done, so scrolling the wheels fires nothing. On Android the field opens the system dialog, and `datetime` asks for the date and then the time. Locale, first day of the week, 12 or 24 hour time and screen reader support come from the OS unless you set them with the props below.

The field opens the picker on press. Pass `open` and `onOpenChange` to open it from somewhere else, for example from a row in a settings list.

The iOS calendar measures itself about 330pt wide and keeps a margin of its own. The component stretches it to the dialog and pulls it out by that margin, so the month, the weekdays and the Done button share one edge. Change the `picker` slot if your dialog uses other padding.

The system picker takes the primary colour as its accent and follows light and dark. The field is the same frame as Input and Select, so the three line up in a form. Put it inside `Field` for a label and an error.

The field is a button whose value is the formatted date. Pass `accessibilityLabel` when the title does not describe the field.

The field is controlled as soon as you pass the `value` key, even as `undefined`. Set the value to `null` or `undefined` and the field shows the placeholder again. Leave `value` out and use `defaultValue` for a field that keeps its own date.

## Time zone, locale and clock

`timeZoneName` goes to the native picker on both platforms, so the wheels and the calendar show the time in that zone, and the `Date` you get back is the instant the user picked there. The default text uses the same zone. The field passes no `timeZoneOffsetInMinutes`, which the native package has deprecated.

`locale` sets the language of the iOS picker and of the default text. Android pickers always follow the system language.

`is24Hour` sets the clock of the Android time dialog and of the default text. iOS has no such switch. Its wheels take the clock from `locale`, or from the device's settings when there is no `locale`. For 24-hour wheels on iOS, pass a locale that uses them, such as `en-GB` or `pt-PT`. Without `is24Hour` the text follows the locale's own clock.

`minuteInterval` applies to the Android time dialog and to the iOS wheels. The iOS calendar has no minutes, so it ignores it.

`display` picks the picker style per platform. iOS defaults to `inline` for `date`, a calendar, and `spinner` for `time` and `datetime`. Android defaults to `default`, a calendar for dates and a clock for times. Android's `calendar` and `clock` values are left out because its dialog treats them as `default`.

The field sends nothing else to the native picker. On Android that means the default dialog design, with no neutral button.

Android can refuse to open the dialog, for example while the app is between Activities. The field then closes as if the user had dismissed the dialog, and the next press opens it again. In `datetime`, a time dialog that fails to open closes the field without committing the date. The exported `openAndroidPicker` does the same: it calls `onDismiss` and then the optional `onError` with the reason.

| Prop                         | iOS                                       | Android                               |
| ---------------------------- | ----------------------------------------- | ------------------------------------- |
| `timeZoneName`               | picker and text                           | both dialogs and text                 |
| `locale`                     | picker and text                           | text only, dialogs follow the system  |
| `is24Hour`                   | text only, wheels follow `locale`         | time dialog and text                  |
| `minuteInterval`             | wheels only                               | time dialog                           |
| `display`                    | `default`, `compact`, `inline`, `spinner` | `default`, `spinner`                  |
| `minimumDate`, `maximumDate` | enforced by the picker                    | date dialog limits days, then clamped |

## Bounds

`minimumDate` and `maximumDate` hold for the instant, not only the day. iOS enforces them in the picker. The Android time dialog takes no bounds, and its date dialog limits calendar days, so a minimum of today at 15:00 still lets the user choose today at 09:00. The field clamps the picked instant to the bounds after the pick, so `onValueChange` gets today at 15:00 in that case. The exported `clampDate(date, minimumDate, maximumDate)` does the same for your own code.

## Format

The default text comes from `formatDateValue(date, mode, { locale, timeZoneName, is24Hour })`, exported from the same file. It formats with `Intl.DateTimeFormat` as a medium date and a short time, in the zone and on the clock you passed. Hermes ships `Intl` on iOS and Android. An unknown zone name makes it throw a `RangeError`. Pass `formatValue` for any other format.
